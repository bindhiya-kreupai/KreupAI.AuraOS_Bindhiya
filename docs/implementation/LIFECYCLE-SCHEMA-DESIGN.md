## 1. Current State

### What Already Exists

**Prisma Model** — `EmploymentHistory` (line 3680):
- 7 change types: PROMOTION, DEMOTION, TRANSFER, LATERAL_MOVE, NEW_HIRE, TERMINATION, REHIRE
- Before/after FK columns for Department, JobProfile, Grade, Location, Manager, Salary, EmploymentType
- Approval workflow (requestedBy, approvedBy, status)
- `isAutoGenerated` flag

**Service Layer** — `apps/web/src/lib/services/employment-history.service.ts`:
- Fully implemented CRUD, timeline queries, statistics
- Approval/rejection workflows
- Auto-creation from employee changes

**UI Page** — `apps/web/src/app/(modules)/core-hr/employment-history/page.tsx`:
- Complete DataPage integration with filtering and approval actions

**Test Suite** — `apps/web/src/lib/services/__tests__/employment-history.service.test.ts`:
- Comprehensive unit tests

**Related Models**: `EmployeeLifeEvent`, `ExitRequest`, `ExitClearance`, `ProbationTracking`, `ProbationReview`, `ConfirmationRequest`, `InterCompanyTransfer`

### What Is Missing

1. **No Employee ↔ EmploymentHistory Prisma relation** — `employeeId` is a bare `String` with no `@relation`
2. **Limited change types** — 7 types; missing PROBATION_START, PROBATION_CONFIRMATION, COMPENSATION_CHANGE, MANAGER_CHANGE, LOCATION_CHANGE, LEAVE_OF_ABSENCE, RETURN_FROM_LEAVE, STATUS_CHANGE
3. **No status tracking** — No `previousStatusId`/`newStatusId` columns
4. **No flexible before/after snapshots** — Only typed FK columns, no JSON for arbitrary data
5. **No provenance tracking** — No `sourceType`, `sourceMetadata`, `isBackfilled`
6. **No composite timeline index** — Only single-column indexes

## 2. Proposed Schema Enhancement

All changes are **non-breaking** — existing columns preserved, new columns nullable or with defaults.

### New Columns to Add to `EmploymentHistory`

```prisma
// Employee Relation (enables includes)
employee Employee @relation("EmployeeHistory", fields: [employeeId], references: [id], onDelete: Cascade)

// Status tracking
previousStatusId  String?
newStatusId       String?

// Flexible before/after snapshots (for non-FK data like allowances, custom fields)
beforeValues  Json?
afterValues   Json?

// Actor (who recorded the event)
actorId  String?

// Provenance
sourceType     String?  @default("MANUAL") // MANUAL, SYSTEM_TRIGGER, IMPORT, MIGRATION, API, WORKFLOW
sourceMetadata Json?    // { "triggeredBy": "...", "batchId": "...", "importFile": "..." }
isBackfilled   Boolean  @default(false)
```

### New Relation on Employee Model

Add to Employee model (after line 308):
```prisma
employmentHistory  EmploymentHistory[]  @relation("EmployeeHistory")
```

### New/Updated Indexes

```prisma
@@index([employeeId, effectiveDate(sort: Desc)])  // Primary timeline query
@@index([tenantId])
@@index([tenantId, employeeId])
@@index([tenantId, changeType])
@@index([tenantId, effectiveDate])
@@index([changeType])
@@index([effectiveDate])
@@index([status])
@@index([tenantId, status])
@@index([isBackfilled])
@@index([isDeleted])
```

## 3. Event Type Mapping (14 Types)

| Event Type | `changeType` Value | What Changes | Key Fields |
|---|---|---|---|
| Hire | `HIRE` | Initial employment record | All "new" fields populated, no "previous" |
| Probation Start | `PROBATION_START` | Status → PROBATION | `previousStatusId`, `newStatusId` |
| Probation Confirmation | `PROBATION_CONFIRMATION` | Status → CONFIRMED, possible salary bump | Status + salary fields |
| Department Transfer | `DEPARTMENT_TRANSFER` | Department changes | `previousDepartmentId`, `newDepartmentId` |
| Position Change | `POSITION_CHANGE` | Job profile/position (promotion, demotion, lateral) | JobProfile, Position, Grade fields |
| Grade Change | `GRADE_CHANGE` | Grade level without role change | `previousGradeId`, `newGradeId` |
| Compensation Change | `COMPENSATION_CHANGE` | Salary/allowance only | Salary fields + `beforeValues`/`afterValues` for allowance detail |
| Manager Change | `MANAGER_CHANGE` | Reporting line | `previousManagerId`, `newManagerId` |
| Location Change | `LOCATION_CHANGE` | Work location | `previousLocationId`, `newLocationId` |
| Leave of Absence | `LEAVE_OF_ABSENCE` | Extended leave | Status fields + `beforeValues` for leave type/dates |
| Return from Leave | `RETURN_FROM_LEAVE` | Back from leave | Status fields |
| Status Change | `STATUS_CHANGE` | Suspension, reactivation | Status fields |
| Termination | `TERMINATION` | Employee exits | Status fields + `beforeValues` for exit details |
| Rehire | `REHIRE` | Former employee returns | All "new" fields populated |

**Legacy values** (PROMOTION, DEMOTION, TRANSFER, LATERAL_MOVE, NEW_HIRE) remain valid in the database. Service layer maps at read time: `NEW_HIRE` → `HIRE`, `PROMOTION`/`DEMOTION` → `POSITION_CHANGE`.

## 4. Backfill Strategy

### Phase 1: Baseline HIRE Records

For every Employee without a HIRE/NEW_HIRE record, create one from their current data:

```sql
INSERT INTO "EmploymentHistory" (
  id, "tenantId", "employeeId", "changeType", "effectiveDate",
  "newDepartmentId", "newJobProfileId", "newGradeId", "newLocationId",
  "newManagerId", "newStatusId",
  status, "isAutoGenerated", "isBackfilled", "sourceType", "sourceMetadata",
  "createdAt", "updatedAt"
)
SELECT
  gen_random_uuid(), c."tenantId", e.id, 'HIRE', e."joiningDate",
  e."departmentId", e."jobProfileId", e."gradeId", e."locationId",
  e."managerId", e."statusId",
  'COMPLETED', true, true, 'MIGRATION',
  jsonb_build_object('backfillRun', 'initial-lifecycle-backfill', 'backfillDate', now()::text),
  now(), now()
FROM "Employee" e
JOIN "Company" c ON e."companyId" = c.id
WHERE NOT EXISTS (
  SELECT 1 FROM "EmploymentHistory" eh
  WHERE eh."employeeId" = e.id AND eh."changeType" IN ('HIRE', 'NEW_HIRE')
);
```

### Phase 2: Backfill from Domain Tables

- **From `ProbationTracking`**: Generate PROBATION_START and PROBATION_CONFIRMATION records
- **From `ExitRequest`**: Generate TERMINATION records (where status = COMPLETED)
- **From `InterCompanyTransfer`**: Generate DEPARTMENT_TRANSFER records (where status = COMPLETED)

### Phase 3: Mark Existing Records

```sql
UPDATE "EmploymentHistory"
SET "isBackfilled" = false, "sourceType" = 'MANUAL'
WHERE "isBackfilled" IS NULL OR "sourceType" IS NULL;
```

### Safety

- All backfill records: `isBackfilled = true`, `sourceType = 'MIGRATION'`
- Idempotent: `NOT EXISTS` guard prevents duplicates
- Run in a transaction; rollback on any failure
- Validate: `COUNT(DISTINCT employeeId WHERE changeType IN ('HIRE','NEW_HIRE'))` = `COUNT(*) FROM Employee`
